# Mutator Image Automation — content-addressed builds, automatic re-pin, pinned agent CLIs

**Status:** Design — ready for review
**Date:** 2026-09-15
**Extends:** `2026-08-28-sandbox-image-distribution-design.md` (digest pins, the manual re-pin
ceremony D11, the image-pins tripwire D12) and `2026-09-13-arena-major-version-design.md` (every
new arena digest needs a human classification).
**Occasion:** PR #67, the OpenCode 2 operator. A checkout ran a two-week-old local mutator with no
`opencode2` in it, doctor called it ready, and the only fix was a manual `make mutator`. The GHCR
side of the same PR needed a hand-dispatched workflow, which rebuilt the arena for no reason.

**How to read this.** §2 is the mental model and §3 the glossary. §4 is the decisions ledger, §5
the design, §6 the flows each kind of person sees. §7 are the invariants — check any change
against them.

---

## 1. Problem

Three failures, all hit on 2026-09-14, plus one drift source.

**A checkout's mutator goes stale silently.** In a repo checkout, `resolve_image`
(`sandbox_preflight.py:94`) returns the mutable tag `nethackers/mutator:latest`, and
`ensure_image` (`:270`) builds it only when it is absent. Nothing ties that image to the files in
the checkout. A developer's image from 2026-08-26 had no `opencode2`; the evolve form showed
"version unknown" and an empty model list, while doctor's presence-only check
(`diagnostics.py:199`) reported ready.

**Publishing a mutator change is manual, and drags the arena along.** Changing
`Dockerfile.mutator` means dispatching `sandbox-images.yml` by hand. That workflow always rebuilds
`nle-base`, the arena and the mutator together, so a mutator-only change mints a new arena digest
that someone must classify in `ARENA_MAJOR_BY_DIGEST`. PR #67 did exactly that (arena `97ba883e…`)
and then needed a hub deploy so the hub would accept the new digest.

**The re-pin commit starts no CI.** The workflow pushes its commit with `GITHUB_TOKEN`, and events
from that token create no workflow runs. After the re-pin on 2026-09-10, an empty commit titled
`ci: verify rebuilt sandbox image pins on the PR head` (`fb8a55f`) was pushed to get the checks to
run.

**The agent CLIs are unpinned.** `npm install -g @anthropic-ai/claude-code @openai/codex
@opencode-ai/cli@beta` takes whatever is current at build time, so two builds of the same files can
ship different agents.

Owner decisions, 2026-09-15:

- automate both publishing (CI) and local checkouts;
- the mutator only — arena re-pins stay manual and deliberate;
- users never run `make`; it is a developer tool;
- make `ghcr.io/dunnolab/nethackers-nle-base` public — **done 2026-09-15**;
- pin the three agent CLI versions.

## 2. Mental model

A mutator image is identified by a **fingerprint of its inputs**: the files its Dockerfile copies
plus the base image it builds on. Same files, same fingerprint.

- **CI** publishes at most one image per fingerprint and records, in the pins file, which
  fingerprint and digest the code ships.
- **A checkout** asks for the image matching its own files: the pinned digest when nothing changed,
  otherwise the fingerprint's image, pulled from GHCR if CI built it or built locally if not.
- **A release** still trusts only digests. A fingerprint is a cache key, not a byte-for-byte promise
  (§10, R2).

## 3. Glossary

| Term | Meaning |
|---|---|
| **base** | The `nle-base` image (compiled NLE + Python deps) that both the arena and the mutator build `FROM`. |
| **mutator inputs** | The files `Dockerfile.mutator` builds from (§5.1) plus the pinned base digest. |
| **mutator hash** | `sha256` over the mutator inputs (§5.1). Written `h-<64 hex>` as an image tag. |
| **pins file** | `src/nethackers/_image_pins.py`, generated by `scripts/repin_images.py`. |
| **full rebuild** | The existing, manually dispatched `sandbox-images.yml`: base + arena + mutator. |
| **mutator rebuild** | The new automatic workflow, `mutator-image.yml`: the mutator alone, on the pinned base. |

## 4. Decisions

- **D1. Identify the mutator by a content hash of its inputs.** Hash file contents as they are in
  the working tree, so uncommitted edits count. One stdlib-only function serves CI, the release gate
  and the CLI. *Rejected:* a git-revision label plus `git diff` (the first proposal — it can only
  warn, and it is blind to uncommitted edits); rebuilding before every run and trusting BuildKit's
  cache (it cannot tell CI when to re-pin, since every build mints a new digest, and the TUI and
  doctor would keep seeing the old image until a run rebuilt it); timestamps.
- **D2. The mutator builds on the pinned base digest, and its hash includes that digest instead of
  the base's own inputs.** The mutator then runs the same compiled NLE the pinned arena scores on,
  and a release's version bump in `pyproject.toml` (which `nle-base/Dockerfile` copies) does not
  trigger a mutator rebuild. *Consequence:* changing the base (`uv.lock`, `nle-base/Dockerfile`)
  needs the full rebuild, as today.
- **D3. Automate the mutator only.** Arena digests keep being minted by the manual full rebuild,
  with a human classifying each one (owner decision).
- **D4. Commit the re-pin with a GitHub App installation token**, so the commit starts the PR's
  checks. *Rejected:* `GITHUB_TOKEN` (starts no runs); a personal access token (needs a machine
  account, long-lived); `[skip ci]` tricks (a skipped required check stays pending).
- **D5. Idempotent by existence.** The workflow builds only when GHCR lacks the fingerprint's tag
  and commits only when the pins differ. That also stops the bot's own commit from causing a
  rebuild loop.
- **D6. Fork PRs build without publishing.** GitHub gives them no secrets and a read-only token.
  After a maintainer merges, the run on `main` publishes and commits the pin to `main`.
- **D7. A checkout resolves to the pinned digest when its hash equals the pinned hash, and
  otherwise to a local ref `nethackers/mutator:h-<hash>`.** `ensure_image` fills that ref by pulling
  the GHCR tag or building locally. A local build is never tagged with the GHCR name.
- **D8. Pin the three agent CLIs in `Dockerfile.mutator`** at the versions in today's pinned mutator
  (`95a62b17…`): `@anthropic-ai/claude-code@2.1.270`, `@openai/codex@0.154.0`,
  `@opencode-ai/cli@0.0.0-beta-19271`. A version bump is an edit to that line, so it changes the
  hash and rebuilds automatically. *Not pinned, known drift:* NodeSource's Node 22 minor (today
  `v22.23.2`), apt packages, and `python:3.11-slim` in the base.
- **D9. No automatic cleanup of local fingerprint images.** A run starts a fresh container
  every iteration, so between iterations nothing holds its image; deleting "old" fingerprints
  from one worktree could break an evolve running in another, and removing a pulled
  fingerprint's last tag can drop the pinned mutator image with it. Old
  `nethackers/mutator:h-*` images stay until the developer removes them.
- **D10. Make the tripwire per image.** Arena and base inputs changed since the last release tag →
  the `ARENA_IMAGE` pin must have changed. Mutator consistency is checked exactly, by hash, at
  release (§5.4), so mutator-only paths leave the regex.
- **D11. Keep QEMU for the arm64 mutator build.** This job doesn't compile NLE, since the base is
  pulled, and it reuses the workflow setup the repo already has. Move to native
  `ubuntu-24.04-arm` runners only if the first measured build is too slow (R5).

## 5. Design

### 5.1 The hash — `src/nethackers/image_inputs.py`

A stdlib-only module, runnable in CI as `PYTHONPATH=src python3 -m nethackers.image_inputs
mutator`.

- **Input list**, one constant: `Dockerfile.mutator`, `docker-entrypoint.sh`,
  `src/nethackers/__init__.py`, and every file under `src/nethackers/arena/` and
  `src/nethackers/contracts/`.
- **Excluded**, mirroring `.dockerignore`: `__pycache__/` directories and `*.pyc` files.
- **Per file:** POSIX path relative to the repo root, the executable bit, and `sha256` of the
  content, sorted by path.
- **Digest:** `sha256("nethackers-mutator-inputs/v1\n" + NLE_BASE_IMAGE + "\n" + one line per
  file)`. The scheme string is bumped to force fresh images when the rules change.
- **A contract test** parses every `COPY` source in `Dockerfile.mutator` and asserts the input list
  covers it, so a new `COPY` can't silently fall outside the hash.

### 5.2 The pins file

Two generated constants join the existing two:

```python
NLE_BASE_IMAGE = (
    "ghcr.io/dunnolab/nethackers-nle-base@sha256:"
    "<64 hex>"
)
MUTATOR_INPUTS = "sha256:<64 hex>"
```

`scripts/repin_images.py` accepts `--nle-base` and `--mutator-inputs`, and can update the mutator
alone, leaving `ARENA_IMAGE` and `NLE_BASE_IMAGE` untouched. The bootstrap base is
`sha256:d03eadf7c4cede31ffe317dc6ea9c230e488a319cd1e561ab7b61d7988c55a8d`, the base
`sandbox-images.yml` built from `6f94cf9` on 2026-09-14 for the current arena and mutator pins.

The full rebuild writes all four constants, and tags its mutator `h-<hash>` computed on its fresh
base, so the two workflows never disagree about what a hash means.

### 5.3 The mutator rebuild — `.github/workflows/mutator-image.yml`

**Triggers:** `pull_request` and `push` to `main`, both filtered to the §5.1 paths plus
`src/nethackers/_image_pins.py`; and `workflow_dispatch`. **Concurrency:** one run per ref,
queued rather than cancelled, so the bot's own push doesn't mark the build that made it
"cancelled".

Steps:

1. Check out the PR's head branch (not the merge commit), so there is a branch to commit to.
2. Compute the mutator hash with §5.1.
3. `docker buildx imagetools inspect ghcr.io/dunnolab/nethackers-mutator:h-<hash>`.
4. **Missing:** build `linux/amd64,linux/arm64` with `--build-arg NLE_BASE=<NLE_BASE_IMAGE>` and
   push it under `h-<hash>` and `sha-<gitsha>`. **Present:** read its digest.
5. If `MUTATOR_IMAGE` or `MUTATOR_INPUTS` differ from the result, run `repin_images.py` for the
   mutator, commit `chore(images): re-pin mutator (h-<first 12>)`, and push it to the head branch
   (or `main`) with a token from `actions/create-github-app-token`, SHA-pinned like the repo's
   other actions. A non-fast-forward push exits cleanly: the newer push triggers its own run.
6. **Fork PRs** (`head.repo.full_name != github.repository`): build amd64 only, push nothing, and
   say in the job summary that publishing happens after merge.

The bot's commit changes `_image_pins.py`, so the workflow runs again. It finds the tag present and
the pins equal, and exits within a minute (D5).

### 5.4 Checks — tripwire and release gate

- **`ci.yml` tripwire** (per image, D10): if `arena/Dockerfile`, `nle-base/Dockerfile`, `uv.lock`,
  `src/nethackers/arena/` or `src/nethackers/contracts/` changed since the last `v*` tag, the
  `ARENA_IMAGE` value must have changed too. `Dockerfile.mutator` leaves this list. Arena and
  contracts code stays on it, because that code also goes into the arena.
- **`publish-pypi.yml` release gate:** before publishing, compute the mutator hash of the tagged
  tree and require it to equal `MUTATOR_INPUTS`, alongside the existing check that both pinned
  digests exist in GHCR. A release can never ship a mutator pin that doesn't match its files.

No pytest check on the hash: on a same-repo PR it would be red until the bot's commit landed, and
on a fork PR red until after merge, which hides real failures.

### 5.5 Resolving and acquiring the mutator in a checkout — `sandbox_preflight.py`

`resolve_image(None, "mutator")`, which stays side-effect-free (it only reads files):

1. An explicit ref (flag or env) wins verbatim. A `.env.stack` file can no longer set the mutator:
   `scripts/stack.py` wrote `NETHACKERS_MUTATOR_IMAGE=nethackers/mutator:latest` into every
   worktree's file, which would bypass this ladder and keep the stale image, so that key is
   ignored there and new stack files omit it.
2. Not a repo checkout → the pinned `MUTATOR_IMAGE` digest — unchanged; this is every user.
3. A checkout → compute the mutator hash of the working tree. Equal to `MUTATOR_INPUTS` → the pinned
   digest. Otherwise → `nethackers/mutator:h-<hash>`.

`ensure_image("nethackers/mutator:h-<hash>", "mutator")`:

1. Present locally → done.
2. `docker pull ghcr.io/dunnolab/nethackers-mutator:h-<hash>` succeeds → `docker tag` it as the
   local ref → done.
3. Otherwise build locally: `docker build -f Dockerfile.mutator --build-arg
   NLE_BASE=<NLE_BASE_IMAGE> --label org.dunnolab.nethackers.image=mutator -t
   nethackers/mutator:h-<hash> <repo root>`, streaming progress as builds do today. This calls
   `docker build` directly rather than `make mutator`, whose `nle-base` prerequisite would compile
   NLE locally.

The arena in a checkout is unchanged: `nethackers/arena:dev`, built via `make` when absent.
`make mutator` stays as a manual developer tool, used with `NETHACKERS_MUTATOR_IMAGE` for
experiments on the base itself.

### 5.6 Doctor

For an `h-` ref in a checkout, `_check_image("mutator")`:

- **present** → `ok`, "present — matches this checkout (h-<first 12>)";
- **absent, GHCR has the tag** → `warn`, the existing "not local yet, but pullable" branch;
- **absent, GHCR doesn't** → `warn`, "not built yet: the image files changed since the pinned
  build, and nethackers builds it on first use". Today this branch is a `fail` whose fix says to
  run `make`; it no longer mentions `make`.

Users' checks are unchanged: a pinned digest is either present, pullable or unreachable.

### 5.7 Docs

- `docs/harness.md`: "It's a beta" becomes a pinned beta build, bumped by editing
  `Dockerfile.mutator`; the parity paragraph under "The information diet" names the shared,
  pinned base.
- `docs/contributing.md`: the image-pins section describes the automatic mutator re-pin and the
  manual arena re-pin, and drops the claim that any re-pin orphans verified scores, which stopped
  being true with the arena major version.
- `docs/troubleshooting.md`: wherever it tells a checkout to rebuild the mutator, say nethackers
  does that on its own.

## 6. Flows

**A maintainer PR that changes the mutator.** Push → the mutator rebuild builds and pushes
`h-<hash>` → it commits the re-pin to the branch → the normal checks run on that commit → merge.
The release carries the new pin. Nobody dispatches anything, and no arena digest appears.

**Any PR that doesn't touch the mutator's files.** The workflow doesn't start, thanks to the path
filter.

**A fork PR that changes the mutator.** CI builds amd64 to prove it builds and publishes nothing.
After merge, the run on `main` publishes the image and commits the pin to `main`.

**A PR that changes arena code, `uv.lock` or the base.** The mutator part is automatic, because
arena code also lives in the mutator. The tripwire then asks for the arena re-pin: the author
dispatches the full rebuild and adds the `ARENA_MAJOR_BY_DIGEST` line, as today.

**Local development.** On `evolve`, opening the TUI, or `doctor`, nethackers computes the hash.
Unchanged files → the pinned image, pulled like any user's. Changes pushed to a branch here → CI's
image, pulled. Unpushed changes, or a fork → built locally on the public base without compiling
NLE, and rebuilt on the next change. Nobody runs `make`.

**Users (pip install).** Unchanged: the pinned digest, pulled on first use.

**Releasing.** Unchanged, plus the release gate (§5.4).

## 7. Invariants

- **I1.** A released `MUTATOR_IMAGE` was built from files whose hash equals the released
  `MUTATOR_INPUTS` (release gate).
- **I2.** `MUTATOR_IMAGE` and `ARENA_IMAGE` build on the same `NLE_BASE_IMAGE`.
- **I3.** Nothing automatic mints an arena digest.
- **I4.** A user without a checkout never builds an image, never sees an `h-` ref, and is never told
  to run `make`.
- **I5.** A local build never carries the GHCR repository name.
- **I6.** `resolve_image` has no side effects.
- **I7.** Re-running the mutator rebuild on an unchanged tree builds nothing and commits nothing.

## 8. Manual setup, once

1. `nethackers-nle-base` public on GHCR — done 2026-09-15.
2. A GitHub App for `dunnolab`: repository permission **Contents: Read and write** (Metadata read
   comes with it), installed on `dunnolab/nethackers` only. Store its Client ID and a private key
   as the repository secrets `IMAGE_BOT_CLIENT_ID` and `IMAGE_BOT_PRIVATE_KEY`.
3. The PR implementing this bootstraps `NLE_BASE_IMAGE` and `MUTATOR_INPUTS`. Its version pins
   change `Dockerfile.mutator`, so that PR is also the first automatic rebuild.

## 9. Testing

- **Hash:** stable across file order; changes with content, the executable bit, or the base digest;
  ignores `__pycache__` and `*.pyc`. The `COPY` coverage contract test.
- **Pins:** `repin_images.py` updates the mutator alone and keeps the arena and base lines
  byte-identical.
- **Resolution:** unchanged checkout → pinned digest; changed → `h-` ref; an explicit ref wins; no
  checkout → pinned digest, with no hashing at all.
- **Acquisition:** pull hit → tag, no build; pull miss → the exact `docker build` argv (base arg,
  label, tag).
- **Doctor:** the three `h-` branches, and no message mentioning `make`.
- **Workflow, on a scratch branch before merge:** a no-op PR skips; a mutator change builds,
  re-pins, and CI runs on the bot's commit; a re-run builds and commits nothing; the fork guard
  keeps secrets out.
- **End to end:** edit a comment in `docker-entrypoint.sh` in a checkout → the evolve form builds
  the new image → doctor `ok` → revert → the pinned digest is used again.

## 10. Risks

- **R1. The input list drifts from the Dockerfile.** Mitigated by the `COPY` contract test.
- **R2. A fingerprint is not a byte-identity.** Node's minor version, apt packages and
  `python:3.11-slim` still drift under an unchanged hash; D8 removes the largest source, the agent
  CLIs. Releases trust digests, never tags.
- **R3. A bot commit races the author's push.** A non-fast-forward is a clean exit, and the newer
  push re-runs.
- **R4. GHCR grows by one mutator per change.** Acceptable at today's rate; add a retention policy
  if it isn't.
- **R5. The arm64 mutator build under QEMU may be slow.** Measure on the first run, and move to
  native arm runners if it is.
- **R6. Updates stop when the App's key expires or is revoked.** The re-pin step fails loudly, and
  the release gate still blocks a mismatched release.
- **R7. Fingerprint images accumulate on developer machines.** Most layers are shared with the
  base and with each other, so each extra image costs its top layers; `docker image ls
  nethackers/mutator` shows them.

## 11. Non-goals

- Automating the arena image, or fixing stale local `nethackers/arena:dev` images in checkouts.
- Pinning Node, apt packages or the base's Python image.
- Bumping the agent CLI versions automatically (Renovate or Dependabot).
