# How Coding-Agent Harnesses Sandbox Untrusted Code Execution

**A field report: per-tool mechanisms, OS primitives, best practices, gotchas — and a tailored recommendation for a local-first, harness-agnostic mutator sandbox (mac + Linux, NLE inside).**

*Researched 2026-08-16 from primary sources (official docs, GitHub repos and source files, engineering posts). Inline URLs cite each claim; synthesis and judgment calls are marked **[inference]**.*

---

## (A) TL;DR + tailored recommendation

**The field has converged.** The two serious harness-native sandboxes — Claude Code's (§B1) and Codex's (§B2) — independently arrived at the same architecture: **Seatbelt (`sandbox-exec`) on macOS + bubblewrap (+seccomp) on Linux**, a **single writable workspace** (CWD + tmp) over a read-mostly filesystem, **default-deny network**, **hard-coded write-denies on the harness's own config and `.git/hooks`** (so the agent can't grant itself powers for the next run), and an **escalation UX** where commands auto-run inside the boundary and prompt only to cross it (Anthropic measured an 84% prompt reduction; they also measured *why* prompts don't work — users approve 93% of them). Network allow-listing is done by a **proxy outside the sandbox** (srt), an **iptables default-DROP allowlist** (the reference devcontainer), or postponed entirely (Codex local: network just off in `workspace-write`). Secrets follow the **sentinel/two-phase pattern**: placeholders inside, real values injected at the proxy (Claude Code masking, Gondolin) or present only during a networked setup phase and removed before the agent runs (Codex cloud).

**Everything else either has no sandbox or wraps one of the above.** Pi ships zero permissions on purpose and points you at containers/VMs (§B3); opencode is approval-rules-only and rejected its own Seatbelt PR, leaving plugins and Docker recipes to fill in (§B4); Cline/goose/Continue/aider/open-interpreter are approval-gated host execution; Cursor is the one IDE that built a real Seatbelt/profile sandbox (§C2). A young "wrap any agent" runtime class is forming above the primitives: NVIDIA **OpenShell** (YAML policy, per-binary egress, inference routing), Docker **Sandboxes** (microVM per agent), **agentbox**-style dev-boxes, **container-use** (container+branch per agent via MCP) (§C).

**The load-bearing facts for our decision:**
1. **No process-level sandbox has resource limits.** Seatbelt, bwrap, Landlock, srt, Codex's sandbox: none can stop a fork bomb or a runaway build — that lives in cgroups v2, i.e., containers (§D3, §E.7). Our #1 hazard therefore rules out a pure srt-style wrapper.
2. **Both vendors bless "container outside, YOLO inside."** OpenAI: put Codex in Docker and run `danger-full-access` inside; Anthropic: the devcontainer "exists precisely so that the agent can run unattended" (§B1, §B2). Wrapping whole CLIs in one Linux container is the *supported* harness-agnostic configuration, not a hack.
3. **NLE seals it.** NLE is a compile-from-source C env that's painful on Apple-Silicon macOS but trivially baked into a linux/arm64 image — the sandbox and the build problem have the same solution (§F, §H).

**Recommendation (detail + checklist in §H):** build **one NLE-baked multi-arch Linux image** containing Python/NLE and all four harness CLIs as a non-root user; run **each mutator invocation as a fresh `docker run --rm` container** with `--pids-limit/--memory/--cpus`, a single workspace volume, env-var API keys, and nothing else mounted; on macOS host all containers in **one shared lightweight VM** (Colima free / OrbStack if licensed), native Docker/Podman on Linux; keep the **scorer in a separate container** (same image, read-only candidate mount, `--network none`, own results volume) so the mutator/scorer wall is mount topology, not policy. Start with open egress (the harness needs its model API; accident-grade doesn't demand an allowlist) and adopt the `init-firewall.sh` allowlist pattern later if wanted. Skip gVisor/microVMs locally (isolation we don't need, overhead we'd pay) and revisit OpenShell/Docker Sandboxes/apple-container as they mature.

## (B) Per-tool deep dives

### B1. Claude Code (Anthropic)

Claude Code has the most layered containment story of any harness today: a **permission system** (rules + modes + hooks) deciding *whether* a tool call runs, an **OS-level Bash sandbox** constraining *what a running command can touch*, an open-sourced **sandbox-runtime (srt)** that can wrap the *whole* process, and a **reference devcontainer** with a default-deny egress firewall for full-container isolation. Anthropic's own framing: "Rather than supervising what the agent does, we supervise what it's *able* to do by enforcing access boundaries through, for example, sandboxes, virtual machines, and egress controls" ([How we contain Claude across products](https://www.anthropic.com/engineering/how-we-contain-claude), May 2026).

#### Permission modes and rules

Docs: [permission modes](https://code.claude.com/docs/en/permission-modes), [permissions](https://code.claude.com/docs/en/permissions).

| Mode (config value) | What runs without asking |
|---|---|
| `default` (labeled "Manual") | Reads only |
| `acceptEdits` | Reads, file edits, common filesystem commands (`mkdir`, `mv`, `cp`…) |
| `plan` | Reads only (analysis before editing) |
| `auto` | Everything, but a second model (a classifier) reviews actions instead of you |
| `dontAsk` | Only pre-approved tools; everything else is denied rather than prompted |
| `bypassPermissions` | Everything — docs say "Isolated containers and VMs only" |

- Set via `claude --permission-mode <mode>`, `permissions.defaultMode` in settings, or Shift+Tab cycling. `--dangerously-skip-permissions` starts in `bypassPermissions`; it is **refused when running as root** on Linux/macOS (the check is skipped inside a recognized sandbox/devcontainer) ([sandboxing docs](https://code.claude.com/docs/en/sandboxing)).
- Even under `bypassPermissions`, explicit **deny/ask rules** still apply, and prompts remain only for a short list (removals targeting `/` or `$HOME`, org-`ask` connector tools, MCP tools marked `requiresUserInteraction`) ([sandbox environments](https://code.claude.com/docs/en/sandbox-environments)).
- **Permission rules** live in `settings.json` under `permissions.allow/deny/ask` with tool-scoped patterns like `Bash(git push *)`, `Read(./.env)`, `WebFetch(domain:github.com)`; they can also be passed per-invocation via `--allowedTools`/`--disallowedTools`. Scopes: managed (MDM/server) > CLI `--settings` > local project `.claude/settings.local.json` > project `.claude/settings.json` > user `~/.claude/settings.json` ([settings](https://code.claude.com/docs/en/settings)).
- Anthropic's motivating telemetry: **"users approved roughly 93% of permission prompts"** — approval fatigue makes human-in-the-loop weak, which drove the sandbox work ([How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)).

#### Hooks as a policy/sandbox mechanism

[Hooks](https://code.claude.com/docs/en/hooks) are user-defined shell commands (or HTTP endpoints/LLM prompts) fired at lifecycle events — `PreToolUse`, `PermissionRequest`, `PostToolUse`, `SessionStart`, etc. A `PreToolUse` hook receives the tool call as JSON on stdin and can emit `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "allow"|"deny"|"ask", "permissionDecisionReason": "..."}}`, or `exit 2` to hard-block (exit 2 cannot be overridden by JSON). This makes hooks a programmable **policy engine**: block `rm -rf`, force `ask` on `git push`, log every command for audit. Two caveats the docs are explicit about: hooks themselves **run with full user permissions on the host**, and hooks are *advisory string-matching* — unlike the OS sandbox they evaluate the command text before it runs, not the process behavior after ([hooks reference](https://code.claude.com/docs/en/hooks)). **[inference]** Hooks are best used for *audit and intent-level policy*, with the OS sandbox as the actual enforcement boundary; a hook that regex-matches `curl` is trivially bypassed by `bash -c "$(base64 -d ...)"`.

#### The built-in sandboxed Bash tool

Docs: [Configure the sandboxed Bash tool](https://code.claude.com/docs/en/sandboxing). Enabled via `/sandbox` in-session or `"sandbox": {"enabled": true}` in settings. Runs on **macOS (Seatbelt, nothing to install), Linux and WSL2 (requires `bubblewrap` + `socat`; optional seccomp filter from `@anthropic-ai/sandbox-runtime` adds Unix-domain-socket blocking)**. Native Windows unsupported.

- **Filesystem policy**: default = read everything (minus denials), **write only the CWD and a session temp dir** (`$TMPDIR` is redirected into the sandbox temp). Configurable via `sandbox.filesystem.allowWrite/denyWrite/denyRead/allowRead`, merged across settings scopes. Git worktrees get an extra write grant to the main repo's shared `.git` (except `hooks/` and `config`).
- **Protected paths — the anti-self-modification list**: even inside writable directories, the sandbox denies writes to the files Claude Code itself loads code/config from: `.claude/settings*`, `.claude/{skills,agents,commands,hooks}`, `.mcp.json`, shell startup files, `.gitconfig`, `.git/hooks` and `.git/config`, `~/.claude` + `~/.claude.json` + the credential store. Rationale, quoted: "A command that could edit those files could grant itself permissions, or add a hook or MCP server that Claude Code runs outside the sandbox." There is **no way to exempt these paths** short of disabling the filesystem layer entirely.
- **Network policy**: all egress goes through **a proxy running outside the sandbox**; nothing is pre-allowed. First use of a new domain prompts (or goes to the auto-mode classifier); `sandbox.network.allowedDomains`/`deniedDomains` pre-seed the list; `strictAllowlist: true` denies instead of prompting; orgs can pin with `allowManagedDomainsOnly`. The built-in proxy filters on the **client-supplied hostname without terminating TLS** by default — the docs warn this leaves room for domain fronting and that "allowing broad domains such as `github.com` can create paths for data exfiltration." An experimental `network.tlsTerminate` makes the proxy a MITM (needed for credential masking); `httpProxyPort`/`socksProxyPort` let you substitute your own inspecting proxy.
- **Credential handling**: `sandbox.credentials` entries with `"mode": "deny"` (block file reads / unset env vars for sandboxed commands) or `"mode": "mask"` — sandboxed commands see a per-session **sentinel value** and the proxy swaps in the real secret only on egress to `injectHosts` (requires `tlsTerminate`; includes AWS SigV4 re-signing support). Important default: **there is no built-in credential deny list** — `~/.aws/credentials` and `~/.ssh` are readable unless you list them. `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` strips Anthropic/cloud credentials from all subprocesses.
- **Approval model**: "auto-allow" mode runs sandboxable commands without prompting (this is the headline UX win — "sandboxing safely reduces permission prompts by 84%" per the [engineering post](https://www.anthropic.com/engineering/claude-code-sandboxing)); commands that fail on a sandbox denial surface the violation to the model, which may retry with `dangerouslyDisableSandbox: true` — that retry goes through the *regular* permission flow. `"allowUnsandboxedCommands": false` (strict mode) kills this escape hatch. `rm` targeting `/` or `$HOME` always re-prompts.
- **Scope limits (their own words)**: "The sandbox isolates Bash subprocesses." Read/Edit/WebFetch run in-process under permission rules; **MCP servers and hooks are separate processes that run unconstrained on the host**; env vars are inherited by default. For one boundary around everything, Anthropic points at srt, devcontainers, or VMs ([sandbox environments](https://code.claude.com/docs/en/sandbox-environments)).

#### `sandbox-runtime` (srt) — the open-source core

Repo: [github.com/anthropic-experimental/sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime) (`@anthropic-ai/sandbox-runtime`, CLI `srt`), "a research preview developed for Claude Code to enable safer AI agents." It wraps **arbitrary commands** — `srt <command>`, or `SandboxManager.wrapWithSandbox(...)` as a TS library — so it is harness-agnostic by construction.

- **Primitives**: macOS = `sandbox-exec` with **dynamically generated Seatbelt profiles** (plus reading the system sandbox-violation log store for real-time alerts); Linux = **bubblewrap** with network-namespace isolation plus a prebuilt **seccomp-BPF `apply-seccomp` binary (x64/arm64) that blocks `socket(AF_UNIX, ...)`**; Windows = alpha via a dedicated `srt-sandbox` local user + Windows Filtering Platform egress filters + NTFS ACLs (README).
- **Filesystem semantics** (from the README, config in `~/.srt-settings.json` or `--settings`): reads are deny-then-allow (`filesystem.denyRead` with `allowRead` re-opening holes), writes are allow-only (`filesystem.allowWrite` with `denyWrite` carve-outs); "Precedence is intentionally opposite for reads vs writes." Mandatory write-denies regardless of config: shell rc files, `.gitconfig`, `.git/hooks/`, `.git/config`, `.vscode/`, `.idea/`, `.claude/commands/`, `.claude/agents/`. macOS paths support git-style globs; **Linux paths are literal only**.
- **Network design**: allow-only. Proxies (HTTP/HTTPS + SOCKS5 for other TCP) run **on the host, outside the sandbox**; on Linux they are reached over **Unix domain sockets bind-mounted into the netns and relayed by `socat`**; on macOS over localhost ports permitted in the Seatbelt profile. `network.allowedDomains` supports wildcards and `:port` suffixes; `allowUnixSockets` and `allowLocalBinding` are explicit opt-ins, with the README warning that allowing `/var/run/docker.sock` "would effectively grant access to the host system."
- **Reading the source** confirms the mechanics. [`src/sandbox/macos-sandbox-utils.ts`](https://github.com/anthropic-experimental/sandbox-runtime/blob/main/src/sandbox/macos-sandbox-utils.ts) emits an SBPL profile that opens `(version 1)` `(deny default ...)`, then `(allow file-read*)` + targeted `(subpath ...)`/`(regex ...)` denies, `(allow file-read-metadata (vnode-type DIRECTORY))` so `realpath()` can traverse denied regions, **move-blocking rules** (denying `file-write-unlink`/`file-write-create` on denied paths *and their ancestors* to kill the `mv .env x; cat x` bypass), and network rules that deny by default and allow only `(remote ip "localhost:{proxyPort}")`. Comments document Seatbelt trivia like `(remote ip "localhost:*")` matching `127.0.0.1`/`::1` but **not** `::ffff:127.0.0.1` (worked around by forcing Java to IPv4 via `JAVA_TOOL_OPTIONS`). [`src/sandbox/linux-sandbox-utils.ts`](https://github.com/anthropic-experimental/sandbox-runtime/blob/main/src/sandbox/linux-sandbox-utils.ts) builds a bwrap line with `--unshare-net --unshare-pid --unshare-user --cap-drop ALL --proc /proc --dev /dev --die-with-parent --new-session`; read-denies are implemented by mounting `--tmpfs` over denied directories (files get `--ro-bind /dev/null`), write confinement by `--ro-bind / /` then re-`--bind`ing the allowed writable paths; inside the sandbox a nested `socat` listens on `localhost:3128`/`1080` and forwards over the bind-mounted Unix sockets to the host proxies, with `HTTP_PROXY`-style env vars pointed at it.
- **Honest limitations** (README): domain filtering doesn't inspect traffic (domain-fronting risk acknowledged); **proxy enforcement on Linux is cooperative** — "programs that ignore environment variables may bypass proxy redirection" (they just get no network, since the netns has no route out — the risk is availability, not escape **[inference]**); `enableWeakerNestedSandbox` (needed under unprivileged Docker, where bwrap can't mount a fresh `/proc`) "considerably weakens security"; macOS `allowAppleEvents` "removes code-execution isolation, not just weakens it"; Linux has no violation monitor (use `strace`).
- **Notably absent: resource limits.** Neither srt nor the built-in Bash sandbox imposes CPU/memory/pids caps — a fork bomb inside the sandbox is still a fork bomb on your host. **[inference]** — confirmed by the absence of any rlimit/cgroup handling in the repo tree and settings schema.
- Wrapping all of Claude Code: `npx @anthropic-ai/sandbox-runtime claude` puts file tools, hooks and MCP servers behind the same boundary; the docs walk through the write grants Claude Code itself needs (`~/.claude`, `~/.claude.json`, `/tmp`, project dir) and warn that on Linux "write grants only apply to paths that already exist" at launch, and that the launch-time deny-list scan "does not cover anything the session creates later, such as `git init`" ([sandbox environments → Sandbox runtime](https://code.claude.com/docs/en/sandbox-environments#sandbox-runtime)).

#### The reference devcontainer + egress firewall

[Devcontainer docs](https://code.claude.com/docs/en/devcontainer); files in [anthropics/claude-code/.devcontainer](https://github.com/anthropics/claude-code/tree/main/.devcontainer). The stated purpose: "Because the container runs Claude Code as a non-root user and confines command execution to the container, you can pass `--dangerously-skip-permissions` for unattended operation." The Anthropic engineering post puts it crisply: "A tight perimeter also means you can relax oversight. Claude Code's reference devcontainer exists precisely so that the agent can run unattended, without per-action approvals" ([How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)). [`init-firewall.sh`](https://github.com/anthropics/claude-code/blob/main/.devcontainer/init-firewall.sh) sets **iptables default policies to DROP on INPUT/FORWARD/OUTPUT**, then ipset-allowlists: GitHub's published CIDRs (fetched live from `api.github.com/meta`), `registry.npmjs.org`, `api.anthropic.com`, `sentry.io`, `statsig.anthropic.com`/`statsig.com`, and VS Code marketplace/update domains; DNS (udp/53) and loopback are allowed; the script self-verifies (example.com must fail, `api.github.com/zen` must succeed). Requires `NET_ADMIN`+`NET_RAW` capabilities via `runArgs`. The docs also warn plainly: with `--dangerously-skip-permissions`, "dev containers do not prevent a malicious project from exfiltrating anything accessible inside the container, including the Claude Code credentials stored in `~/.claude`" — and to avoid mounting `~/.ssh` or cloud credential files.

#### The engineering posts, distilled

- [Claude Code sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing) (announced the feature + srt open-sourcing): "Effective sandboxing requires *both* filesystem and network isolation. Without network isolation, a compromised agent could exfiltrate sensitive files like SSH keys; without filesystem isolation, a compromised agent could easily escape the sandbox." Internal result: 84% fewer permission prompts.
- [How we contain Claude across products](https://www.anthropic.com/engineering/how-we-contain-claude) (May 2026; good summary by [Simon Willison](https://simonwillison.net/2026/May/30/how-we-contain-claude/)) documents three tiers — claude.ai code execution in **gVisor** containers server-side; Claude Code with the OS sandbox + human-in-the-loop; Claude Cowork in a **full VM** (Apple Virtualization framework / Windows HCS) — plus war stories: Claude "helpfully" escaping sandboxes; a phishing-style prompt injection where "across 25 retries... Claude completed the exfiltration 24 times" (only egress controls stopped it, not model-layer classifiers); an exfiltration *through an allowlisted domain* (`api.anthropic.com` Files API with an attacker's key — allowlists grant capabilities, not just destinations); the pre-trust-dialog config-parsing hole. Their three closing principles: **(1)** "Design for containment at the environment layer first, then steer behavior at the model layer." **(2)** "Match isolation strength to the user's capacity for oversight." **(3)** "Be wary of custom components. Battle-tested hypervisors, syscall filters, and container runtimes have survived more adversarial attention than anything you'll build."

### B2. Codex CLI (OpenAI)

Codex is the other reference implementation of harness-native OS sandboxing, and the only major harness that wrote its own kernel-level policy for **three** OSes. Docs note: the in-repo `docs/sandbox.md` is now a stub pointing at the hosted docs ([developers.openai.com/codex/security](https://developers.openai.com/codex/security) → [sandboxing](https://learn.chatgpt.com/docs/sandboxing)); the fullest historical text lives in the tagged release docs ([rust-v0.42.0 docs/sandbox.md](https://raw.githubusercontent.com/openai/codex/rust-v0.42.0/docs/sandbox.md), [config.md](https://raw.githubusercontent.com/openai/codex/rust-v0.42.0/docs/config.md)); current source lives in dedicated crates [`codex-rs/sandboxing/`](https://github.com/openai/codex/tree/main/codex-rs/sandboxing), [`codex-rs/linux-sandbox/`](https://github.com/openai/codex/tree/main/codex-rs/linux-sandbox), and (new) `codex-rs/windows-sandbox-rs/`.

#### Sandbox modes

Selected with `--sandbox`/`-s` or `sandbox_mode` in `~/.codex/config.toml`:

- **`read-only`** — "The agent can inspect files, but it can't edit files or run commands without approval": full-disk read (`(allow file-read*)`), no writes, no network.
- **`workspace-write`** (the local default) — read everything; **write only the writable roots**: the cwd, `/tmp` (unless `exclude_slash_tmp`), `$TMPDIR` if set (unless `exclude_tmpdir_env_var`), plus configured `writable_roots` (`SandboxPolicy::WorkspaceWrite` in [`codex-rs/protocol/src/protocol.rs`](https://raw.githubusercontent.com/openai/codex/main/codex-rs/protocol/src/protocol.rs)). **`network_access` defaults to `false`** — a sandboxed command has no egress at all until you flip `[sandbox_workspace_write] network_access = true`.
- **`danger-full-access`** — no restrictions; the historical docs recommend it precisely "if Codex is running in an environment that provides its own sandboxing (such as a Docker container)" or where native sandboxing is unsupported.

**Anti-self-escalation inside writable roots**: each writable root carries `read_only_subpaths` "to ensure that folders containing files that could be modified to escalate the privileges of the agent (e.g. `.codex`, `.git`, notably `.git/hooks`) under a writable root are not modified" — the protected basenames are the constant `PROTECTED_METADATA_PATH_NAMES = [".git", ".agents", ".codex"]` ([`protocol/src/permissions.rs`](https://raw.githubusercontent.com/openai/codex/main/codex-rs/protocol/src/permissions.rs)). Consequence the docs own up to: plain `git commit` fails inside the sandbox by default and needs an approval. Same design instinct as Claude Code's protected paths — the harness's own config and git hooks are the privilege-escalation surface.

#### Approval policies and the escalation loop

`approval_policy` / `--ask-for-approval` (`-a`): **`untrusted`** (auto-approve only "known safe" read-only commands per `is_safe_command()`; ask for everything else), **`on-request`** (default — "The model decides when to ask the user for approval"; the old `on-failure` is now just a serde alias for it), **`never`** (failures return to the model, never escalate), plus a newer `granular` object form ([`approval_mode_cli_arg.rs`](https://raw.githubusercontent.com/openai/codex/main/codex-rs/utils/cli/src/approval_mode_cli_arg.rs), [config reference](https://learn.chatgpt.com/docs/config-file/config-reference)). The famous `--full-auto` (historically = `workspace-write` + `on-failure`) has been **removed from current main**, succeeded by `--approve-for-me` (alias `--not-so-yolo`: auto-reviewer + on-request + workspace-write). `--dangerously-bypass-approvals-and-sandbox` / **`--yolo`** is documented in-source as "EXTREMELY DANGEROUS. Intended solely for running in environments that are externally sandboxed" ([`shared_options.rs`](https://raw.githubusercontent.com/openai/codex/main/codex-rs/utils/cli/src/shared_options.rs)).

The **escalate-on-sandbox-denial flow** ([`core/src/tools/orchestrator.rs`](https://raw.githubusercontent.com/openai/codex/main/codex-rs/core/src/tools/orchestrator.rs)): first attempt runs sandboxed; on `SandboxErr::Denied` the orchestrator constructs a retry reason (e.g. `"Network access to \"<host>\" is blocked by policy."`), asks the user, then reruns with `SandboxType::None` if approved. Two safeguards worth copying: a strict auto-review mode always re-reviews the unsandboxed retry ("retrying without the sandbox requires a fresh guardian review"), and **policies with denied-read paths refuse unsandboxed retry entirely** "because bypassing the sandbox would silently grant those reads" ([`tools/sandboxing.rs`](https://raw.githubusercontent.com/openai/codex/main/codex-rs/core/src/tools/sandboxing.rs)). The model can also proactively request escalated permissions per-command. This is the same "auto inside the boundary, prompt at the boundary" UX as Claude Code's `dangerouslyDisableSandbox` retry.

#### macOS implementation: Seatbelt

[`codex-rs/sandboxing/src/seatbelt.rs`](https://github.com/openai/codex/blob/main/codex-rs/sandboxing/src/seatbelt.rs) runs commands under the **hardcoded** `/usr/bin/sandbox-exec` ("to defend against an attacker trying to inject a malicious version on the PATH"). The profile is assembled from [`seatbelt_base_policy.sbpl`](https://raw.githubusercontent.com/openai/codex/main/codex-rs/sandboxing/src/seatbelt_base_policy.sbpl) — "inspired by Chrome's sandbox policy", starting **`(deny default)`** and allowing process-exec/fork (children inherit the profile), same-sandbox signals, writes to `/dev/null` only, an enumerated `sysctl-read` whitelist, PTY support, and POSIX shm/semaphores for Python multiprocessing/PyTorch — plus dynamically generated file rules: per-root `(allow file-write* ...)` parameterized clauses with `(require-not (subpath ...))` exclusions for `.git`/`.codex`/`.agents` (including regexes so a protected dir can't even be *created*), and deny-read globs paired with `(deny file-write-unlink ...)` "so a denied path cannot be probed through destructive filesystem operations" — the same move-blocking insight as srt. **Network**: with `(deny default)`, no network rules = no network; `network_access = true` appends `(allow network-outbound)(allow network-inbound)` plus [`seatbelt_network_policy.sbpl`](https://raw.githubusercontent.com/openai/codex/main/codex-rs/sandboxing/src/seatbelt_network_policy.sbpl), which allowlists the mach services DNS/TLS need (`com.apple.SecurityServer`, `com.apple.networkd`, `com.apple.ocspd`, `com.apple.trustd.agent` — note this is exactly the trustd access whose absence breaks Go CLIs under Claude Code's stricter profile). A managed-proxy mode allows only loopback proxy ports + DNS and fails closed. You can exercise the sandbox standalone (`codex debug seatbelt <cmd>` historically; the debug entrypoints live on in `codex-rs/cli/src/debug_sandbox.rs`). Users flagged `sandbox-exec`'s deprecation early ([openai/codex#215](https://github.com/openai/codex/issues/215)); OpenAI ships on it anyway, like everyone else.

#### Linux implementation: bubblewrap (now default) + seccomp, Landlock as legacy fallback

Major evolution documented in [`codex-rs/linux-sandbox/README.md`](https://raw.githubusercontent.com/openai/codex/main/codex-rs/linux-sandbox/README.md): "**Bubblewrap is the default filesystem sandbox**"; the original **Landlock + mount protections remain as an explicit legacy fallback** (`features.use_legacy_landlock = true`). The bwrap path: `--ro-bind / /` read-only root, writable roots re-`--bind`ed, protected subpaths re-applied read-only (symlinked/missing ones masked with `/dev/null` mounts), `--unshare-user --unshare-pid`, `--unshare-net` when network is restricted without proxy routing, fresh `--proc /proc`; prefers system `bwrap`, falls back to a **bundled** `codex-resources/bwrap` with a warning. WSL2 uses the normal path; WSL1 unsupported.

In-process hardening ([`linux-sandbox/src/landlock.rs`](https://raw.githubusercontent.com/openai/codex/main/codex-rs/linux-sandbox/src/landlock.rs)): `PR_SET_NO_NEW_PRIVS` plus a **seccomp filter** (built with `seccompiler`, default-allow, matched syscalls → `EPERM`) that always denies `ptrace`, `process_vm_readv/writev`, and `io_uring_*` (io_uring being a known filter-bypass channel for network syscalls **[inference]**), and in network-restricted mode denies `connect/bind/listen/accept/sendto/...` while restricting `socket`/`socketpair` to `AF_UNIX` (`recvfrom` deliberately allowed so tools like `cargo clippy` work). The legacy Landlock path uses **ABI V5, best-effort compat**, read `/`, write to writable roots + `/dev/null`, and **fails closed** (`SandboxErr::LandlockRestrict`) if the kernel can't enforce. For Docker environments the guidance is explicit: if the container blocks the needed Landlock/seccomp/userns APIs, "configur[e] your Docker container so that it provides the sandbox guarantees you are looking for and then run `codex` with `--sandbox danger-full-access`... within your container" (rust-v0.42.0 docs/sandbox.md). A native **Windows** sandbox now exists too (`codex-rs/windows-sandbox-rs/`: restricted tokens, ACLs, Windows Filtering Platform — per file names **[inference]**; PowerShell uses it, WSL2 uses the Linux path per [the docs](https://learn.chatgpt.com/docs/sandboxing)).

#### Environment variable policy

`[shell_environment_policy]` controls what subprocesses inherit ([`protocol/src/config_types.rs`](https://raw.githubusercontent.com/openai/codex/main/codex-rs/protocol/src/config_types.rs), applied with `env_clear()` + explicit re-population in [`core/src/exec_env.rs`](https://raw.githubusercontent.com/openai/codex/main/codex-rs/core/src/exec_env.rs)): `inherit = all|core|none`, default exclude globs **`*KEY*`, `*SECRET*`, `*TOKEN*`**, plus `exclude`/`set`/`include_only`. Note the default flipped over time: v0.42.0 stripped secret-looking vars by default; current main inherits all unless you opt in. Sandboxed children get marker vars `CODEX_SANDBOX_NETWORK_DISABLED=1` and `CODEX_SANDBOX=seatbelt` so scripts can detect the sandbox ([`core/src/spawn.rs`](https://raw.githubusercontent.com/openai/codex/main/codex-rs/core/src/spawn.rs)).

#### Codex cloud: the two-phase model

([cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environment), [agent internet access](https://learn.chatgpt.com/docs/cloud/internet-access); container reference image [openai/codex-universal](https://github.com/openai/codex-universal).) Each task runs in a container from the `universal` image. **Phase 1 (setup)**: setup/maintenance scripts run **with internet access** ("so you can install dependencies") and with **secrets** available. **Phase 2 (agent)**: "For security reasons, secrets are removed before the agent phase starts", and "By default, Codex blocks internet access during the agent phase." When you enable agent-phase internet, you pick a **domain allowlist** — None / "Common dependencies" preset (`github.com`, `pypi.org`, `npmjs.com`, `docker.com`, `maven.org`, ...) / All — plus an **HTTP method restriction to `GET`/`HEAD`/`OPTIONS`** (blocking POST/PUT exfil channels), with an explicit warning about prompt injection and exfiltration risks. This is the cleanest published statement of the "secrets and network for deps first, then sealed agent" pattern, and it's the direct template for a mutator loop's *build-then-experiment* split. **[inference on the last clause]**

#### Config surface (summary)

```toml
# ~/.codex/config.toml  ($CODEX_HOME/config.toml)
approval_policy = "on-request"       # untrusted | on-request | never | { granular = {...} }
sandbox_mode    = "workspace-write"  # read-only | workspace-write | danger-full-access

[sandbox_workspace_write]
writable_roots         = ["/extra/dir"]
network_access         = false       # default false
exclude_tmpdir_env_var = false
exclude_slash_tmp      = false
```

Profiles (`--profile`, `[profiles.<name>]` historically; now layered `<name>.config.toml` files plus a granular `[permissions.<name>]` system with built-ins `:read-only`, `:workspace`, `:danger-full-access`) bundle these ([config reference](https://learn.chatgpt.com/docs/config-file/config-reference)).

### B3. Pi (pi.dev)

**What it is.** Pi is a deliberately minimal terminal coding harness by Mario Zechner (badlogic), maintained under [earendil-works/pi](https://github.com/earendil-works/pi) and documented at [pi.dev](https://pi.dev/); npm `@earendil-works/pi-coding-agent` (formerly `@mariozechner/pi-coding-agent` / repo `badlogic/pi-mono`). The model gets exactly four built-in tools — `read`, `write`, `edit`, `bash` — and everything else is extensions/skills/packages ("primitives, not features").

**Sandboxing/permission model: none built in, by design.** The README states it flat out: "Pi does not include a built-in permission system for restricting filesystem, process, network, or credential access" ([repo](https://github.com/earendil-works/pi)). Bash commands (and `!` shell escapes) run **directly on the host with the launching user's permissions**. A maintainer discussion confirms the stance — pi runs "full YOLO" by default and expects you to bring your own boundary ([discussion #1874](https://github.com/earendil-works/pi/discussions/1874)). Pi.dev frames permission gates, path protection and sandboxing as things you implement as **TypeScript extensions** aligned with your threat model ([pi.dev](https://pi.dev/)).

**The three blessed containment patterns**, from [`packages/coding-agent/docs/containerization.md`](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/containerization.md):

1. **Gondolin extension** — pi runs on the host (auth/API keys stay on host), but `read`/`write`/`edit`/`bash`/`grep`/`find`/`ls` are overridden to execute inside a **local Linux micro-VM**, with the host CWD mounted at `/workspace` and changes synced back. [Gondolin](https://github.com/earendil-works/gondolin) (also earendil-works) is "Local Linux micro-VMs with programmable network and filesystem control": QEMU by default (experimental `krun` backend), macOS + Linux, arm64 the most-tested path, **programmable HTTP/TLS egress policy in JavaScript** with request/response hooks, and secret injection via placeholder tokens so real keys never enter the guest — the same sentinel pattern as Anthropic's credential masking. **[inference]** This is the most architecturally interesting of the three: harness on host, tools in VM, policy in code.
2. **Plain Docker** — run the whole `pi` process in a container (`docker run --rm -it -e ANTHROPIC_API_KEY -v "$PWD:/workspace" -v pi-agent-home:/root/.pi/agent pi-sandbox`). The doc is honest that "provider API keys enter the container."
3. **OpenShell** — run pi inside NVIDIA's policy-controlled sandbox runtime (see §C), which can keep raw model API keys *outside* the sandbox by routing inference through `https://inference.local`.

**pi-sandbox extension** ([pi.dev/packages/pi-sandbox](https://pi.dev/packages/pi-sandbox), `pi install npm:pi-sandbox`): a community extension adding interactive permission prompts (abort / allow-for-session / project / global) and OS-level bash wrapping — "Bash commands are wrapped with `sandbox-exec` (macOS) or `bubblewrap` (Linux)" — plus interception of read/write/edit against filesystem policy. Under the hood it delegates to [`@carderne/sandbox-runtime`](https://github.com/carderne/sandbox-runtime), a published fork of Anthropic's srt. Config in `~/.pi/agent/sandbox.json` / `.pi/sandbox.json`; needs `ripgrep`; its own docs flag that some relaxations "open significant security loopholes."

**Bottom line**: Pi outsources containment entirely — which makes it the cleanest illustration that OS-level wrapping (srt-fork extension, Gondolin VM, container, OpenShell) can be bolted onto a harness that never asked for it. Detail on Pi's *own* mechanisms is thin because there deliberately are none.

### B4. opencode (opencode.ai / SST → Anomaly)

**What it is.** A popular open-source terminal coding agent (repo now [anomalyco/opencode](https://github.com/anomalyco/opencode)). Its containment model is **permission rules, not an OS sandbox**: shell commands run directly on the host.

**Permission model** ([docs/permissions](https://opencode.ai/docs/permissions/)): per-tool keys — `edit` (covers edit/write/patch), `bash` (matched against *parsed* commands), `read`, `glob`, `grep`, `webfetch`, `websearch`, `task` (subagents), `skill`, `external_directory` (paths outside the project), `doom_loop` (the same tool call repeated 3+ times) — each resolving to `"allow" | "ask" | "deny"`, with wildcard patterns and per-agent overrides:

```json
{
  "permission": {
    "bash": { "*": "ask", "git *": "allow", "rm *": "deny" }
  },
  "agent": { "build": { "permission": { "bash": { "git commit *": "deny" } } } }
}
```

Defaults are notably permissive: most tools default to `"allow"`; only `doom_loop` and `external_directory` default to `"ask"`, and reads of `.env` / `.env.*` default to `"deny"`. Because `bash` matching operates on the parsed command string, it inherits the classic string-matching weaknesses (indirection via `sh -c`, interpreters, downloaded scripts) **[inference]**. A separate experimental **policies** layer controls resource access (currently just `provider.use` allow/deny) — governance, not sandboxing ([docs/policies](https://opencode.ai/docs/policies/)).

**Sandboxing: proposed upstream, rejected; ecosystem filled the gap.**
- PR [#21538](https://github.com/anomalyco/opencode/pull/21538) added experimental opt-in **macOS Seatbelt sandboxing** (`sandbox-exec -p <generated profile>`; `workspace-write`/`read-only` modes, extra roots, `excluded_commands`, `bash:unsandboxed` escalation on denial — visibly modeled on Codex/Claude Code). It was auto-closed unmerged in May 2026 under the repo's reaction-count cleanup policy.
- [`opencode-sandbox`](https://www.npmjs.com/package/opencode-sandbox) — a plugin that wraps every bash invocation with `@anthropic-ai/sandbox-runtime` (Seatbelt/bwrap); note its documented fail-open behavior: "if anything goes wrong during sandbox initialization... commands run normally without sandbox."
- [`opencodebox`](https://github.com/fityannugroho/opencodebox) — "Just OpenCode, but runs in an isolated sandbox. Powered with bubblewrap" (Linux).
- Docker's official recipe runs opencode inside a **Docker Sandboxes** microVM ([docs.docker.com/ai/sandboxes/agents/opencode](https://docs.docker.com/ai/sandboxes/agents/opencode/)); community blogs cover plain-Docker ([danb.me](https://danb.me/blog/opencode-docker/)) and hand-rolled Seatbelt profiles ([aminroosta](https://aminroosta.github.io/tools/llm/security/macos/2026/02/25/sandboxing-opencode-on-macos.html)).

**Bottom line**: opencode's built-in story is approval-based and host-native; treat it like Pi for sandboxing purposes — bring an external boundary.

### B5. agentbox (github.com/rcarmo/agentbox)

**What it is.** A batteries-included **dev-box container** for running coding agents, by Rui Carmo ([repo](https://github.com/rcarmo/agentbox), ~147 stars). The README's stance is refreshingly plain: "There's no perfect way to sandbox agents (yet), but containers are a practical start."

**Design** (from the README and [Dockerfile](https://github.com/rcarmo/agentbox/blob/main/Dockerfile)):
- Base: `FROM debian:trixie-slim`; installs build-essential, cmake, git, tmux, ripgrep, Python dev headers, Homebrew, uv, Bun, Node/Go toolchains; **preinstalls agents**: Copilot CLI, Codex, and Pi (via `bun add -g @openai/codex ... pi-acp`, `brew install copilot-cli ...`), with `make` targets for opencode, Gemini CLI, Toad, mistral-vibe.
- Runs as an unprivileged `agent` user, with **PUID/PGID env vars** for host-UID mapping of the `-v $(pwd):/workspace` mount.
- Services (SSH :22, RDP :3389 in the `:gui` variant, Docker daemon) are **all off by default**, enabled by `ENABLE_SSH/ENABLE_RDP/ENABLE_DOCKER=true`; Docker-in-Docker "needs to run in privileged mode... (it's better than nothing)".
- **Network isolation is a roadmap item, not implemented**; gVisor/Kata are likewise roadmap.

**What it really protects against.** Accident-grade containment: the host filesystem (minus the mounted workspace) and host processes are out of reach, and the box is disposable. It is *not* adversary-grade: the `agent` user has **passwordless sudo** (`agent ALL=(ALL) NOPASSWD:ALL`) and a hardcoded weak password (`agent:smith`), DinD wants `--privileged` (a documented host-escape surface), and there's no egress control — any secret you pass in can leave. **[inference]** agentbox is best read as the "one warm dev container per machine, agents inside" pattern done pragmatically — exactly the shape to study for a mutator box, minus its sudo/privileged conveniences.

## (C) The broad landscape

### C1. Container-for-agents tools

- **Dagger container-use** ([github.com/dagger/container-use](https://github.com/dagger/container-use), Apache-2.0, ~4k stars, "Experimental") — an MCP server, powered by the Dagger engine, where "each agent gets a fresh container in its own git branch"; you review work with plain `git checkout <branch>`, watch "complete command history and logs of what agents actually did," and can drop into any agent's terminal. Because it's MCP, it works with "Claude Code, Cursor, and other MCP-compatible agents" — harness-agnostic at the protocol level, though the harness must actually route its work through the MCP tools rather than its native Bash. **[inference on the caveat]**
- **Devcontainers as sandbox** ([containers.dev](https://containers.dev/)) — the general pattern of §B1's reference container: a spec'd Docker environment your editor attaches to, with the agent installed inside; Anthropic publishes a [Claude Code devcontainer feature](https://github.com/anthropics/devcontainer-features) and the hardened reference with the egress firewall. Enforcement is conventional (nothing stops running the agent outside it) — Anthropic's own docs call it "a convention rather than an enforcement boundary" ([sandbox environments](https://code.claude.com/docs/en/sandbox-environments)).
- **microsandbox** ([github.com/microsandbox/microsandbox](https://github.com/microsandbox/microsandbox), Apache-2.0, ~7.6k stars) — self-hosted **microVM** platform on **libkrun**: "average boot times under 100 milliseconds" on Apple Silicon; macOS (Apple Silicon), KVM Linux, WHP Windows; Rust/Python/TS/Go SDKs plus an MCP server and agent-skills for Claude Code/Cursor. The strongest local isolation class (own guest kernel) at near-container startup cost.
- **llm-sandbox** ([github.com/vndee/llm-sandbox](https://github.com/vndee/llm-sandbox)) — Python library for running LLM-generated snippets in **Docker, Podman, or Kubernetes** backends with per-run "CPU, memory, and execution time limits" and network controls; integrations for ~11 agent frameworks + MCP. Note its own caveat: "Security policies are advisory. `session.is_safe(code)` returns a verdict — it does not block execution." Snippet-runner shaped (code-interpreter), not a harness wrapper.
- **codebox-api** ([github.com/shroominic/codebox-api](https://github.com/shroominic/codebox-api), MIT) — "the simplest cloud infrastructure for your LLM Apps": a code-interpreter backend with `local`, `docker`, and hosted (`sk-*`) modes; the isolation story is the backend you pick — local mode is convenience, not confinement. **[inference]**
- **Claude-in-Docker community wrappers** — a large genre; two representative points: **textcortex/claude-code-sandbox** ([repo](https://github.com/textcortex/claude-code-sandbox), archived Feb 2026) ran Claude with `--dangerously-skip-permissions` in a container, *copied* (not bind-mounted) the repo for "true isolation," auto-discovered and mounted credentials read-only, and surfaced each commit for interactive review/PR; **RchGrav/claudebox** ([repo](https://github.com/RchGrav/claudebox), ~1.1k stars) is a maintained "ultimate Claude Code Docker environment" with 15+ toolchain profiles and a built-in **network allowlist firewall** (`allowlist` command, `--disable-firewall` opt-out). The equivalent genre exists for opencode (§B4: opencodebox, opencode-docker images).
- **agentbox** — covered in depth in §B5; the "one dev-box with all the agents installed" corner of this space.

### C2. Harnesses/IDE agents with approval gates but no (or new) OS sandboxes

- **goose (Block)** ([github.com/block/goose](https://github.com/block/goose)) — extensible local agent (MCP-native). Containment is permission-mode based: **Completely Autonomous** (default), **Smart Approval** (risk-based auto-approval), **Manual Approval**, and **Chat Only**, with per-tool `always_allow`/`never_allow` overrides in `permission.yaml` (docs mirror: [DeepWiki permission modes](https://deepwiki.com/block/goose/6.2-permission-modes-and-tool-approval)). Tools execute on the host; goose contributors also experiment with external Seatbelt wrappers ([michaelneale/agent-seatbelt-sandbox](https://github.com/michaelneale/agent-seatbelt-sandbox)).
- **open-interpreter** ([github.com/OpenInterpreter/open-interpreter](https://github.com/OpenInterpreter/open-interpreter)) — the archetypal "runs code on your machine" agent: host execution with y/n confirmation by default, an experimental `--safe` mode that scans generated code with semgrep ([SAFE_MODE.md](https://github.com/OpenInterpreter/open-interpreter/blob/main/docs/SAFE_MODE.md)), and an experimental Docker integration for full isolation ([isolation docs](https://docs.openinterpreter.com/safety/isolation)). Still actively released as of Aug 2026.
- **aider** ([aider.chat](https://aider.chat/)) — runs on the host with no sandbox; shell/test commands it proposes run with user confirmation, and the project's answer to isolation is its official Docker image ([docs/install/docker](https://aider.chat/docs/install/docker.html)). Representative of the "the git repo is the blast radius" school. **[inference on characterization]**
- **Cline** (VS Code) ([docs.cline.bot/features/auto-approve](https://docs.cline.bot/features/auto-approve)) — human-in-the-loop approval per file edit/command/browser action, with granular **Auto Approve** categories and a **YOLO mode** that "auto-approves everything"; the docs call YOLO dangerous and it exists mainly for their CLI (`cline --yolo`). `.clineignore` blocks file access by pattern. No OS sandbox — approval is the boundary.
- **Continue** ([continue.dev](https://docs.continue.dev/)) — same family: agent-mode tool calls gated by per-tool policies (ask/auto/exclude); execution on host.
- **Cursor** — the exception in the IDE group: Cursor built a real OS sandbox for agent terminal commands ([blog: Implementing a secure sandbox for local agents](https://cursor.com/blog/agent-sandboxing), [run modes docs](https://cursor.com/docs/agent/security/run-modes)). On macOS it uses **Seatbelt via `sandbox-exec`**, generating the profile dynamically from workspace/admin settings and `.cursorignore`, constraining "the behavior of an entire subprocess tree" (their blog is also one of the better public explainers of Seatbelt's status: "introduced in 2007 and deprecated in 2016, but still used by critical third-party applications like Chrome"). Config via `sandbox.json` (network policy, extra read/write paths, temp-dir writes, shared build caches); commands needing full access fall back to an approval prompt — same escalation UX as Codex/Claude Code. A cautionary tale on defaults: an analysis of early builds showed sandboxed reads still reaching secrets ([luca-becker.me](https://luca-becker.me/blog/cursor-sandboxing-leaks-secrets/)).
- **Windsurf** ([docs.windsurf.com](https://docs.windsurf.com/)) — Cascade auto-executes commands subject to user allow/deny lists and an auto-execution setting; host execution, approval-gated. **[not independently deep-dived]**

### C3. Process-sandbox wrappers (OS-native, no containers)

- **srt / @anthropic-ai/sandbox-runtime** — §B1; wraps any command in Seatbelt/bwrap + egress proxy. The category archetype.
- **@carderne/sandbox-runtime** ([github.com/carderne/sandbox-runtime](https://github.com/carderne/sandbox-runtime)) — maintained fork of srt ("A lightweight sandboxing tool for enforcing filesystem and network restrictions on arbitrary processes at the OS level, without requiring a container"), used by pi-sandbox (§B3); adds a bundled Windows helper.
- **landrun** ([github.com/Zouuup/landrun](https://github.com/Zouuup/landrun)) — "Run any Linux process in a secure, unprivileged sandbox using Landlock. Think firejail, but with kernel-level security and minimal overhead." Flags like `--rox/--rw/--connect-tcp/--bind-tcp`; needs Linux 5.13+ (6.7+ for TCP rules, newer ABIs for unix-socket scoping); `--best-effort` degrades gracefully. Linux-only by nature — a lovely primitive for the Linux half of a thin wrapper, useless for the mac half. **[inference on the last clause]**
- **opencodebox / pi-sandbox** — harness-specific instances of the same idea (§B4, §B3).

### C4. Purpose-built agent runtimes read in primary sources

- **NVIDIA OpenShell** ([github.com/NVIDIA/OpenShell](https://github.com/NVIDIA/OpenShell), [docs](https://docs.nvidia.com/openshell/about/overview), Apache-2.0, alpha, ~8.2k stars) — an open-source "safe, private runtime for autonomous AI agents": agents (Claude Code, Codex, opencode, Copilot CLI natively; Pi and others via `--from`) run *unmodified* inside sandboxes created with `openshell sandbox create -- <agent>`, governed by **declarative YAML policy across four domains — filesystem, process (both locked at creation), network, inference (both hot-reloadable)**. Docs describe Landlock-based filesystem confinement and seccomp process restrictions on Linux; the README describes the substrate as "container supervision and policy-enforced egress routing," requiring **Docker, Podman, or host virtualization**, on **Linux, macOS (Apple Silicon), or WSL2 (experimental)**. Distinctives: no outbound connectivity by default, **per-destination and per-binary egress**, credentials injected as env vars (never written to the sandbox filesystem), and — uniquely — **inference as a first-class policy channel**: model API calls are rerouted through a privacy router that strips caller credentials and injects backend ones, so raw provider keys can stay outside the sandbox. Alpha, "single-player mode," but the closest existing thing to a harness-agnostic, cross-platform agent jail.
- **Docker Sandboxes** ([docs.docker.com/ai/sandboxes](https://docs.docker.com/ai/sandboxes/)) — Docker's 2026 product running coding agents in **microVM** sandboxes, each with its own Docker daemon, filesystem, and network; workspace mounting syncs your project in; launched as `sbx run claude` (per-agent configs for Codex/opencode/etc. on the [agents page](https://docs.docker.com/ai/sandboxes/agents/)). The `sbx` CLI is "free to use, including for commercial work" (org governance is paid) and per Anthropic's docs it is "a free, standalone product from Docker that does not require Docker Desktop" ([sandbox environments](https://code.claude.com/docs/en/sandbox-environments)).
- **Gondolin** ([github.com/earendil-works/gondolin](https://github.com/earendil-works/gondolin)) — see §B3: local QEMU/krun Linux micro-VMs with JavaScript-programmable VFS mounts and HTTP/TLS egress policy, secrets injected as placeholders; macOS + Linux, arm64-first. Built to give agents "generated code without human review" a place to run.
- Hosted microVM platforms (E2B, Modal, Morph, Daytona, etc.) are deliberately out of scope here — covered in the prior report; they solve the same problem with someone else's kernel and a network hop.

## (D) OS primitives primer

Four escalating isolation classes: **process sandboxes** (same kernel, restricted syscall/file/network surface), **containers** (same kernel + namespaces + cgroups), **user-space kernels** (gVisor — syscalls emulated), and **VMs/microVMs** (separate guest kernel). Every harness in §B lives in class 1; every "run the agent in a box" tool in §C lives in classes 2–4.

### D1. Linux process-level primitives

- **bubblewrap** ([github.com/containers/bubblewrap](https://github.com/containers/bubblewrap)) — the workhorse under Claude Code, Codex, srt, opencodebox, and Flatpak. An unprivileged sandboxing tool built on **user namespaces** ("a feature in the Linux kernel... which allows unprivileged users to use container features"); the historical setuid fallback mode "has been removed." You compose a mount namespace from flags (`--ro-bind`, `--bind`, `--tmpfs`, `--proc`, `--dev`, `--unshare-pid`, `--unshare-net`, `--die-with-parent`, `--new-session`). Two caveats from its own README: bwrap "is responsible for" nothing policy-wise — "whatever program constructs the command-line arguments for bubblewrap... is responsible for defining its own security model"; and **seccomp is optional, caller-supplied** (hence srt shipping its own `apply-seccomp` binary, §B1). Also no resource limits: pure confinement, zero throttling.
- **Landlock** ([docs.kernel.org/userspace-api/landlock.html](https://docs.kernel.org/userspace-api/landlock.html)) — an **unprivileged LSM** (kernel ≥5.13) letting a process voluntarily restrict its own (and its children's) filesystem access by path-beneath rules, no namespaces required. ABI has grown: v4 (kernel 6.7) adds TCP bind/connect restriction, v6 (6.12) IPC scoping, v9 pathname-unix-socket control (per [landrun](https://github.com/Zouuup/landrun), which wraps it as a CLI). Codex used it as its original Linux sandbox and keeps it as a fail-closed fallback at ABI V5 (§B2). Limits: rules attach at restrict-time ("files or directories opened before sandboxing are not subject to... restrictions" — landrun README), no fine-grained egress (no domain concept), and old-kernel fleets need best-effort degradation.
- **seccomp-BPF** ([kernel docs](https://docs.kernel.org/userspace-api/seccomp_filter.html)) — syscall filtering on syscall number + register values. Its structural blindspot: filters **cannot dereference user-space pointers**, so no path-based or address-based decisions — which is why srt's Unix-socket block is global rather than per-path (§B1) and why Codex's network lockdown must enumerate socket-family constants and also deny `io_uring_*` (a whole alternate syscall surface) and `ptrace`/`process_vm_*` (§B2). Almost always deployed *inside* a namespace boundary, as the second layer.
- **AppArmor / SELinux** — the two mainline MACs. AppArmor (Ubuntu/SUSE; [apparmor.net](https://apparmor.net/)) is path-based profiles per executable; its 2023+ role in this story is mostly as the thing *restricting* sandboxes: Ubuntu's `apparmor_restrict_unprivileged_userns=1` default gates userns creation behind profiles (see §F). SELinux (Fedora/RHEL; [selinuxproject.org](https://selinuxproject.org/)) is label-based MAC; in container land it's what makes a stray bind-mount unreadable until you add `:z`/`:Z`. Neither is something you'd hand-roll per-agent policy in today — they're substrate. **[inference]**
- **firejail** ([github.com/netblue30/firejail](https://github.com/netblue30/firejail)) — long-standing desktop-app sandbox with per-app profiles. Its architecture is its criticism: a **setuid-root** binary with a large option surface, and it has paid for it — e.g. **CVE-2022-31214**, where "by crafting a bogus Firejail container that is accepted... as a join target, a local attacker can enter an environment in which... NO_NEW_PRIVS... is not activated" and escalate to root via `su`/`sudo` ([Gentoo GLSA 202305-19](https://security.gentoo.org/glsa/202305-19), [SentinelOne writeup](https://www.sentinelone.com/vulnerability-database/cve-2022-31214/)). Fine for desktop apps; the agent-sandboxing ecosystem has uniformly chosen unprivileged bwrap/Landlock instead. **[inference on the last clause]**
- **nsjail** ([github.com/google/nsjail](https://github.com/google/nsjail)) — Google's process-isolation tool combining namespaces, **kafel** seccomp policies, rlimits, and cgroups in one CLI/config file; the CTF and grading-infrastructure standard. More knobs (and more resource control) than bwrap, less ubiquity in distro repos.

### D2. macOS: Seatbelt / sandbox-exec (and App Sandbox)

One primitive with two faces. **App Sandbox** is the supported, entitlement-based product for signed apps. **`sandbox-exec`** is the CLI that runs any command under an **SBPL profile** — a Scheme-like policy language (`(version 1)` `(deny default)` `(allow file-read* (subpath ...))` `(allow network-outbound (remote ip "localhost:8080"))` `(allow mach-lookup (global-name ...))`) that filters file ops, network ops, mach services, Apple Events, sysctls, and more, inherited by the whole subprocess tree. It has been **formally deprecated since ~10.11 with no CLI replacement** ([apple/containerization#737](https://github.com/apple/containerization/issues/737) asks Apple directly), yet it *is* the mechanism under App Sandbox and under Chrome, [Bazel](https://bazel.build/docs/sandboxing), Codex (§B2), Claude Code/srt (§B1), and Cursor ([blog](https://cursor.com/blog/agent-sandboxing)) — deprecation here means "unversioned, undocumented, folklore-driven," not "gone." What Seatbelt does *not* give you: resource limits (no cgroup analog on macOS), domain-level egress (allow/deny per socket target only — hence everyone's localhost-proxy pattern), or protection from what TCC/Apple Events can reach once allowed. Profile authorship gotchas are cataloged in §F.

### D3. Containers and the laptop runtimes that host them

A Linux container = **namespaces (isolation) + cgroups v2 (resource limits) + capability dropping + a default seccomp profile** — the only class in this primer that natively answers the fork-bomb question: `docker run --pids-limit` maps to the cgroup [pids controller](https://docs.kernel.org/admin-guide/cgroup-v2.html), `--memory`/`--cpus` to memory/cpu controllers ([Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/), [`docker run` reference](https://docs.docker.com/reference/cli/docker/container/run/)); Docker additionally applies a default seccomp profile and drops most capabilities ([Docker security docs](https://docs.docker.com/engine/security/)). [Podman](https://podman.io/) is the daemonless, rootless-friendly equivalent.

On **Apple-Silicon macOS**, all of this runs inside a Linux VM; the runtime choice is really "which VM manager":

| Runtime | What it is | Cost/licensing | Notes |
|---|---|---|---|
| [Colima](https://github.com/abiosoft/colima) | CLI wrapper over [Lima](https://lima-vm.io/) VMs exposing docker/containerd/k8s | MIT, free | `--vm-type vz` (Apple Virtualization.framework) + virtiofs + optional Rosetta for x86 images; the default free choice |
| [Lima](https://lima-vm.io/) | The underlying "Linux Machines" VM manager | Apache-2.0, free | What you script if you want the VM raw |
| [OrbStack](https://orbstack.dev/) | Polished Docker Desktop replacement (Docker + Linux machines) | Free personal; **commercial use requires a paid license** (~$8/user/mo, [licensing](https://docs.orbstack.dev/licensing)) | Reputation: fastest/lightest of the GUI options |
| [Podman machine / Podman Desktop](https://podman.io/) | Podman's managed VM (QEMU/vz; libkrun option) | Apache-2.0, free | Rootless by default |

### D4. User-space kernels and microVMs

- **gVisor / runsc** ([gvisor.dev](https://gvisor.dev/docs/architecture_guide/performance/)) — an OCI runtime where a user-space kernel (the Sentry) implements Linux syscalls, so guest code never talks to the host kernel directly. Structural cost: "application system calls must traverse additional layers"; worst for syscall-bound workloads ("high-performance data stores and static network services"), near-native for CPU-bound work; platform matters (ptrace "highest structural costs by far"; Systrap recommended; KVM cheap interception). Linux-only as a runtime — on macOS it can only live inside your Linux VM anyway. This is what claude.ai's server-side code execution runs on (§B1). For a local accident-grade loop it's defense you pay latency for without needing. **[inference on the last clause]**
- **Kata Containers** ([katacontainers.io](https://katacontainers.io/)) — OCI-compatible "containers as lightweight VMs": each pod/container gets its own guest kernel via QEMU/cloud-hypervisor/firecracker. Adversarial-grade kernel isolation with container UX; requires (nested) virtualization, which makes it awkward inside macOS Linux VMs. microVM platforms (Firecracker et al.) are the hosted-provider version of the same idea — out of scope here (prior report).

### D5. Windows, briefly

**WSL2** is a managed utility VM running a real Linux kernel — Claude Code and Codex both treat it as "Linux" for sandboxing (bubblewrap works; WSL1 doesn't — §B1, §B2). **Windows Sandbox** ([Microsoft docs](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/)) is a disposable, hypervisor-isolated Windows desktop — good for manual detonation, not loop automation. **AppContainer** + restricted tokens + WFP is the native process-isolation toolkit — exactly what srt's Windows alpha (`srt-sandbox` user + WFP egress filters + NTFS ACLs, §B1) and Codex's new `windows-sandbox-rs` (§B2) assemble.

## (E) Best practices (the convergent patterns, as of mid-2026)

Across Anthropic, OpenAI, NVIDIA, Docker, and the OSS wrappers, the same design keeps re-emerging. Each pattern below is practiced by at least two independent implementations.

1. **Two boundaries or none: filesystem *and* network.** Anthropic: "Effective sandboxing requires *both* filesystem and network isolation" — each alone is defeated via the other ([claude-code-sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)). OpenShell ships four coupled policy domains; Codex pairs workspace-write with network-off. A files-only sandbox leaks data; a network-only sandbox gets rewired from inside.
2. **Single writable workspace; read-mostly everything else.** Claude Code: write = CWD + session tmp; Codex workspace-write: CWD + `/tmp` + `$TMPDIR`; srt: allow-only writes. Reads stay broad for usability, with explicit deny-lists for secrets — and note both Anthropic and Codex default to *not* blocking `~/.ssh`-class reads; you must opt in (`sandbox.credentials`, `denyRead`).
3. **Default-deny egress + allow-list, enforced by a proxy *outside* the sandbox.** srt's host-side HTTP/SOCKS proxies over bind-mounted Unix sockets; Claude Code's prompt-per-new-domain; the devcontainer's iptables DROP + ipset; Gondolin's programmable egress; OpenShell's per-binary egress. The proxy lives outside the boundary so compromised code can't reconfigure it. Corollary everyone learned: **`--network none` breaks pip/npm/git the agent legitimately needs** — hence proxy-with-allowlist rather than airgap.
4. **Secrets stay outside; sentinels or two-phase setup inside.** Three independent inventions of the same idea: Claude Code credential masking (sentinel in env, proxy injects real value on egress to `injectHosts`), Gondolin placeholder tokens, OpenShell inference routing (strip caller creds, inject backend creds); and Codex cloud's two-phase model (setup with network+secrets → secrets removed for the agent phase). If a real secret never enters the sandbox, exfiltration of it is a type error.
5. **Auto-approve inside the boundary; escalate at the boundary.** The entire point of sandboxing in these harnesses is prompt reduction: Claude Code auto-allow (–84% prompts), Codex's escalate-on-sandbox-denial, opencode's proposed `bash:unsandboxed` permission. The prompt moves from "may I run this command?" to "may I cross the boundary?" — rarer and far more meaningful.
6. **Protect the harness's own config from the harness.** Claude Code's protected-paths list and srt's mandatory denies (`.claude/*`, `.git/hooks`, shell rc, `.mcp.json`) exist because a sandboxed process that can edit the sandbox's config wins on the *next* run. Any wrapper you build must deny writes to its own policy files, hook dirs, and the caller's dotfiles.
7. **Resource limits are the container layer's job — process sandboxes don't have them.** Seatbelt and bwrap-based sandboxes (srt, Codex native) impose **no CPU/memory/pids caps**; fork-bomb protection comes from cgroups v2 (`docker run --pids-limit --memory --cpus`, systemd-run properties) or rlimits. If runaway processes are a primary hazard — as in an evolutionary loop — you need cgroups, i.e., a container or a systemd scope, not just a sandbox profile. **[inference]** from the absence of limits in srt/Codex sandbox code plus Docker/cgroup docs.
8. **Audit at the harness layer (hooks/logs), enforce at the OS layer.** Hooks (`PreToolUse`), OpenShell's "full audit trail of every allow and deny," srt's violation store and macOS violation-log tap. String-matching hooks are for visibility and intent-policy; the kernel is for enforcement.
9. **Deterministic, pinned environments; destroy-and-recreate over in-place reset.** Anthropic's devcontainer pins Claude Code and disables auto-update for reproducibility; OpenShell *locks* filesystem/process policy at creation — "changing them requires destroying and recreating the sandbox"; claude.ai uses per-session ephemeral gVisor containers. Ephemerality is also the cheapest cleanup: `docker run --rm` beats any reset script.
10. **Prefer battle-tested primitives over custom orchestration.** Anthropic, after their incidents: "Be wary of custom components. Battle-tested hypervisors, syscall filters, and container runtimes have survived more adversarial attention than anything you'll build" — in every incident their standard primitives held and the custom glue broke ([How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)).
11. **Match isolation strength to oversight capacity and threat model.** Anthropic's tiering (OS sandbox for developers who read bash → full VM for Cowork's non-technical users) is the general rule: for our accident-grade threat model, a container is proportionate; gVisor/microVMs buy adversarial-grade kernel isolation we don't need locally. **[inference]** applied to our case.

## (F) Known gotchas / failure modes

**macOS / Seatbelt**
- `sandbox-exec` has been **deprecated since ~10.11** yet has no CLI-usable replacement; Apple still uses Seatbelt to implement App Sandbox, and Bazel, Chromium, Codex, and Anthropic all still ship on it. See the discussion in [openai/codex#215](https://github.com/openai/codex/issues/215), Apple's non-answer in [apple/containerization#737](https://github.com/apple/containerization/issues/737), and [Bazel's sandboxing docs](https://bazel.build/docs/sandboxing). Practical risk is API removal someday, not present breakage. The SBPL language is unversioned and folklore-documented.
- **`/tmp` is a symlink to `/private/tmp`** (same for `/var` → `/private/var`); profiles must match post-resolution paths or rules silently miss. srt handles this by resolving paths and allowing `file-read-metadata` on directories so `realpath()` works inside denied regions (see §B1 source notes).
- **Read-denies are bypassable via rename unless you also block moves**: srt emits explicit `file-write-unlink`/`file-write-create` denies on denied paths *and ancestors* to stop `mv secret x; cat x`.
- Go-built CLIs (`gh`, `terraform`, `gcloud`) **fail TLS verification under Seatbelt** because they can't reach `com.apple.trustd.agent`; Claude Code's workarounds are `excludedCommands` or the explicitly-weakening `enableWeakerNetworkIsolation` ([troubleshooting](https://code.claude.com/docs/en/sandboxing#troubleshooting)).
- **Apple Events are a sandbox exit**: allowing them (for `open`/`osascript`) "removes code-execution isolation" — sandboxed code can drive unsandboxed apps ([sandboxing docs](https://code.claude.com/docs/en/sandboxing#security-limitations)).
- Seatbelt loopback matching misses IPv4-mapped IPv6 (`::ffff:127.0.0.1`) — Java needs `-Djava.net.preferIPv4Stack=true` (srt source comment).

**Linux / bubblewrap / namespaces**
- **Ubuntu 23.10/24.04+ restricts unprivileged user namespaces via AppArmor** (`kernel.apparmor_restrict_unprivileged_userns=1`), which breaks bubblewrap — and therefore Claude Code's and Codex's Linux sandboxes — plus Chrome/Electron sandboxes ([Ubuntu's explainer](https://discourse.ubuntu.com/t/understanding-apparmor-user-namespace-restriction/58007); [Launchpad bug #2046844](https://bugs.launchpad.net/ubuntu/+source/apparmor/+bug/2046844), "AppArmor user namespace creation restrictions cause many applications to crash with SIGTRAP"; a whole repo exists just to fix Codex on 24.04 — [makash/codex-ubuntu24-bubblewrap-fix](https://github.com/makash/codex-ubuntu24-bubblewrap-fix)). Fix: ship an AppArmor profile for `bwrap` with the `userns,` rule (Claude Code's docs give the exact profile — `profile bwrap /usr/bin/bwrap flags=(unconfined) { userns, ... }` — [sandboxing docs](https://code.claude.com/docs/en/sandboxing#set-up-linux-and-wsl2)) or, bluntly, `sysctl kernel.apparmor_restrict_unprivileged_userns=0` persisted in `/etc/sysctl.d/`.
- **bwrap inside an unprivileged container can't mount a fresh `/proc`** — hence srt's `enableWeakerNestedSandbox` (bind the outer `/proc`), which "considerably weakens security"; nested sandboxes generally degrade.
- bwrap gives **no resource limits and no syscall filtering by itself**; seccomp must be supplied (srt ships `apply-seccomp` purely to block `AF_UNIX` sockets). Fork bombs ride straight through every process-level sandbox in §B — resource limits only exist at the cgroup layer (`docker run --pids-limit --memory --cpus`, [Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/); or `systemd-run --scope -p TasksMax=`) — pair one in, always.
- Linux srt **read-deny is launch-time and literal-path only** (tmpfs-over-directory); globs unsupported, paths created later uncovered — materially weaker than the macOS side (srt README, Claude docs).

**Containers**
- **Mounting `/var/run/docker.sock` = root on the host** — the daemon is root and trusts any client that can write the socket; from inside, `docker run -v /:/mnt --privileged ...` hands over the host filesystem ([Quarkslab: Why is exposing the Docker socket a really bad idea?](https://blog.quarkslab.com/why-is-exposing-the-docker-socket-a-really-bad-idea.html), [Netdata: docker.sock is root access](https://www.netdata.cloud/guides/docker/docker-socket-security/)). The srt README says allowing it through the sandbox "would effectively grant access to the host system"; the same applies to DinD `--privileged` (agentbox does this knowingly). If the agent needs to build images, prefer rootless/isolated daemons (Docker Sandboxes gives each microVM its own daemon).
- **`--network none` breaks the agent's legitimate installs** (pip/npm/git) — the reason everyone converges on egress-proxy-with-allowlist instead.
- **Credential leakage via convenience mounts and permissive read defaults**: `~/.ssh`, `~/.aws`, `~/.netrc`, `~/.gitconfig`, and inherited env vars. Anthropic's devcontainer docs tell you outright not to mount host secrets; Claude Code's sandbox inherits parent env unless you scrub (`sandbox.credentials`, `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`); Codex flipped its default from stripping `*KEY*/*SECRET*/*TOKEN*` vars to inheriting everything (§B2). Read-everything defaults bite too — an analysis of Cursor's early sandbox showed sandboxed commands could still read secrets the profile hadn't denied ([luca-becker.me](https://luca-becker.me/blog/cursor-sandboxing-leaks-secrets/)).
- Docker Desktop is heavyweight on laptops and **licensed** (paid above the employee/revenue threshold); OrbStack is commercial-free-for-personal; Colima/Lima/Podman/Rancher Desktop are the free paths (details in §D).

**Cross-cutting**
- **Symlink/absolute-path escapes**: validate after resolving. Anthropic (Cowork): "Symlink resolution has to happen *before* path validation, not after, or a symlink inside an authorized folder can point outside and escape" ([How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)). srt re-checks symlinked protected paths mid-session.
- **The holes outside the boundary**: in Claude Code's per-command sandbox, **MCP servers and hooks run unsandboxed on the host**; any harness-level sandbox that only wraps `bash` leaves in-process tools and plugins outside. Wrap the whole process (srt/container) if that matters.
- **The agent disabling its own sandbox**: escape hatches exist by design (`dangerouslyDisableSandbox` retry, `excludedCommands`, editable `settings.local.json`). Mitigations: strict mode (`allowUnsandboxedCommands: false`), managed-settings pinning, protected paths, and keeping policy files outside the writable set. Anthropic has watched Claude "helpfully escape a sandbox in order to complete a task."
- **Allowlists grant capabilities, not destinations**: the Cowork incident exfiltrated data through the *allowlisted* `api.anthropic.com` using an attacker's API key. Broad `github.com` ≈ write access to every repo on GitHub.
- **Domain fronting** can slip past hostname-only (non-TLS-terminating) proxies — acknowledged in both srt's README and Claude Code's docs.
- **Approval fatigue is measurable**: 93% of prompts approved; a control users always click is not a control ([How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)).
- **Tool incompatibilities inside sandboxes**: watchman/jest hang (run `--no-watchman`), `docker` CLI can't work inside srt-style sandboxes, browser-auth flows fail without Apple Events. Budget for an `excludedCommands`-style relief valve.
- **gVisor/microVM overhead** is real for syscall-heavy work (details §D); for accident-grade local use, plain containers are the right point on the curve. **[inference]**
- **NLE-style native builds on Apple Silicon**: NLE compiles NetHack C sources at install (needs CMake ≥3.28, flex/bison, etc. — [NetHack-LE/nle](https://github.com/NetHack-LE/nle)); macOS builds have a long failure history ([facebookresearch/nle#28](https://github.com/facebookresearch/nle/issues/28)) and in our own experience are painful on arm64 macs — while the repo ships a `docker/` directory with maintained Linux images. An env that only reliably builds on Linux is itself an argument for a Linux-container sandbox on mac. **[project context + inference]**

## (H) Tailored recommendation + prototype checklist

### H1. Framing the choice

Requirements recap: **local-first** (personal Apple-Silicon macs + Linux boxes), **featherweight**, **harness-agnostic** (must wrap Codex, Claude Code, Pi, opencode, and whatever ships next), a **live Python + built NLE** for the mutator to experiment against, **accident-grade** threat model (own model's code, no secrets in reach; hazards = fork bombs/runaway processes, out-of-workspace writes, and keeping the mutator walled off from the sealed scorer).

Three candidate shapes:

**(a) Thin per-OS process wrapper (srt-style: bwrap on Linux, Seatbelt on macOS), NLE installed natively on each host.**
- *For*: genuinely featherweight (no VM, no image, ~0 startup); [srt](https://github.com/anthropic-experimental/sandbox-runtime) already exists, wraps arbitrary commands, and is exactly harness-agnostic (`srt codex ...`, `srt claude ...`); native speed.
- *Against — and these are disqualifying for this use case*: **(1)** it does nothing about the **#1 stated hazard**: neither Seatbelt nor bwrap imposes CPU/memory/pids limits, so a fork bomb or runaway compile still takes down the host (§E.7). You'd bolt on `systemd-run --scope -p TasksMax=...` on Linux and have **no good macOS equivalent** (ulimits are per-process, not per-tree, and macOS has no cgroups). **(2)** It requires **NLE built natively on Apple-Silicon macOS** — the exact pain this project wants to stop paying (§F, NLE gotcha). **(3)** You maintain two divergent policy dialects (SBPL + bwrap args) and inherit every Seatbelt/AppArmor gotcha in §F, and mac-vs-Linux mutator runs execute in different environments, which is poison for comparing evolutionary results. **[inference]**

**(b) One warm Linux container per machine (NLE-baked image); harness CLIs stay on the host; their tool executions are redirected into the container** (the [Gondolin](https://github.com/earendil-works/gondolin)/[container-use](https://github.com/dagger/container-use) topology).
- *For*: host-native harness UX (auth, config, TUIs on the host); single canonical Linux env for code execution; NLE prebaked.
- *Against*: **redirection is per-harness work, which breaks harness-agnosticism.** Pi lets you override its `bash`/`read`/`write` tools via an extension (that's literally how Gondolin integrates, §B3); Claude Code hooks can *block* but not transparently *re-route* Bash; Codex and opencode offer no supported tool-override at all — so you end up writing N adapters (or fragile PATH-shim games) for N harnesses, and the harness process itself plus its file tools still run unsandboxed on the host. **[inference]** This shape shines when you commit to *one* harness; it fights you when the whole point is wrapping many.

**(c) Run the entire harness CLI inside a per-run container from one NLE-baked image** (the [agentbox](https://github.com/rcarmo/agentbox)/[Anthropic devcontainer](https://code.claude.com/docs/en/devcontainer)/[Codex-in-Docker](https://raw.githubusercontent.com/openai/codex/rust-v0.42.0/docs/sandbox.md) topology).
- *For*: **one boundary, any harness** — inside a container a harness is just a process, so "wrap future CLIs" is `npm install -g <new-cli>` in the Dockerfile. It is the **vendor-blessed** configuration for exactly this: OpenAI — "configur[e] your Docker container so that it provides the sandbox guarantees you are looking for and then run `codex` with `--sandbox danger-full-access`... within your container"; Anthropic — the devcontainer "exists precisely so that the agent can run unattended," with `--dangerously-skip-permissions` legal as a non-root user (§B1, §B2). It solves the **NLE-on-mac problem outright** (build linux/arm64 once; every mac runs the identical image), gives **cgroups v2 resource limits for free** (`--pids-limit --memory --cpus` — the only option that actually addresses fork bombs), makes **destroy-and-recreate** free (`--rm`), and makes the **scorer wall** a mount-topology fact rather than a policy hope.
- *Against*: needs a Linux VM on macOS (mitigated below — one shared VM, many containers); provider API keys enter the container (fine at accident-grade; keep them env-var-scoped, never mount `~/.ssh`/`~/.aws` — §F); container startup ~0.5–2 s per run (amortize with a warm container if the loop is chatty). **[inference on latency]**

### H2. Recommendation

**Choose (c): one NLE-baked Linux image; each mutator invocation runs the whole harness CLI inside a fresh `docker run --rm` container with cgroup caps; on macOS, host the containers in a single shared lightweight VM (Colima or OrbStack); keep the scorer in a separate container with read-only inputs.** This is the only option that simultaneously satisfies harness-agnosticism (any CLI is just a process), the fork-bomb/runaway hazard (cgroups), the NLE-on-Apple-Silicon problem (Linux userland everywhere), and determinism across the fleet (one image digest) — and it is the configuration both OpenAI and Anthropic explicitly design their "externally sandboxed" modes for. The srt-style wrapper (a) is the right tool for *interactive* use of one harness on trusted-ish work; it is the wrong chassis for an unattended evolutionary loop whose top hazard is resource exhaustion. **[inference — recommendation]**

Concretely, per mutation step:

```bash
docker run --rm \
  --name "mut-${GEN}-${IDX}" \
  --pids-limit 512 --memory 8g --memory-swap 8g --cpus 4 \
  --security-opt no-new-privileges \
  -v "mut-${GEN}-${IDX}-ws:/workspace" -w /workspace \
  -e ANTHROPIC_API_KEY -e OPENAI_API_KEY \
  nethackers/mutator:<digest> \
  timeout 1800 claude -p "$PROMPT" --dangerously-skip-permissions
# or: ... codex exec --yolo "$PROMPT"   (Codex refuses nothing inside; sandbox_mode=danger-full-access)
# or: ... pi -p "$PROMPT"               (pi is YOLO by default — the container IS its sandbox)
# or: ... opencode run "$PROMPT"        (config: permission.bash="allow" etc.)
```

Notes on the shape:
- **Weight budget**: on Linux this is native containers — effectively free. On macOS, run **one** VM per machine via [Colima](https://github.com/abiosoft/colima) (MIT, free, `colima start --vm-type vz --mount-type virtiofs`, backed by [Lima](https://lima-vm.io/)) or [OrbStack](https://orbstack.dev/) (faster and lighter in practice, but commercial use requires a paid license, ~$8/user/mo — free for personal use per [docs.orbstack.dev/licensing](https://docs.orbstack.dev/licensing)); avoid Docker Desktop (heavier; paid above 250 employees/$10M revenue — [docker.com licensing](https://docs.docker.com/subscription/desktop-license/)). All containers share that VM, so marginal cost per mutator is a cheap Linux process with cgroups, not a VM. [Podman](https://podman.io/) machine is the drop-in daemonless alternative if you prefer; Apple's own [`container`](https://github.com/apple/container) (VM-per-container, macOS 26+, pre-1.0) is worth watching but too young to standardize on. **[inference on maturity]**
- **Network**: start with default bridge egress **allowed** — the harness inside must reach `api.anthropic.com`/OpenAI, and the mutator legitimately pip-installs; accident-grade doesn't require an allowlist, and `--network none` would break the harness itself (§F). The upgrade path when wanted is exactly Anthropic's [`init-firewall.sh`](https://github.com/anthropics/claude-code/blob/main/.devcontainer/init-firewall.sh) pattern (default-DROP + ipset allowlist of model APIs + pypi/npm/github, needs `NET_ADMIN`) or an out-of-container squid/tinyproxy — i.e., the §E.3 proxy pattern.
- **Bake, don't install**: NLE + Python + gymnasium + the harness CLIs are **baked into the image** (two-phase thinking, §E.4/§B2-cloud: dependency network happens at image build; run time needs only model-API egress). Named volumes cache `uv`/npm and persist harness auth (`CLAUDE_CONFIG_DIR` on a volume — devcontainer precedent, §B1).
- **Non-root `agent` user** in the image (Claude Code hard-refuses `--dangerously-skip-permissions` as root, §B1; agentbox's PUID/PGID trick handles bind-mount ownership, §B5). No `--privileged`, no `/var/run/docker.sock` mount, ever (§F).
- **The scorer wall is mount topology**: the mutator writes only its own workspace volume. At evaluation time, the loop (host-side) exports the candidate at a commit boundary (git bundle / tarball), and the **scorer runs in a separate container** — same NLE image for env-determinism — with the candidate mounted **read-only**, `--network none` (a scorer needs no egress), and its own results volume the mutator never mounts. No shared writable surface ⇒ the mutator cannot touch scores or scorer inputs; the interesting failure mode left is reward-hacking *within* the candidate code, which is an eval-design problem, not a sandbox problem. **[inference — design]**
- **Off-the-shelf alternates for the same shape**, if you'd rather adopt than script: **[Docker Sandboxes](https://docs.docker.com/ai/sandboxes/)** (`sbx run claude` — free CLI, microVM per sandbox with its own dockerd; heavier per-instance than shared-VM containers, product-shaped rather than loop-scriptable) and **[NVIDIA OpenShell](https://github.com/NVIDIA/OpenShell)** (`openshell sandbox create -- <agent>` with YAML policy, per-binary egress, inference routing — the most principled harness-agnostic jail, but alpha, and it sits on Docker/Podman anyway). Both are worth a half-day spike each; neither beats ~30 lines of `docker run` for a loop you fully control. **[inference]**

### H3. Prototype checklist

1. **Image** (`Dockerfile`, multi-arch `linux/arm64` + `linux/amd64`): Debian/Ubuntu base → build deps (`cmake>=3.28`, `build-essential`, `flex`, `bison`, `python3-dev` — per [NetHack-LE/nle](https://github.com/NetHack-LE/nle)) → `uv` + Python env with `nle` + `gymnasium` compiled at build → Node 20+ → `npm i -g @anthropic-ai/claude-code @openai/codex @earendil-works/pi-coding-agent opencode-ai` → non-root `agent` user → smoke test `python -c "import nle, gymnasium; gymnasium.make('NetHackScore-v0').reset()"` in CI for both arches.
2. **Runtime bring-up**: mac — `colima start --cpu 6 --memory 12 --vm-type vz --mount-type virtiofs`; Linux — rootful or rootless Docker/Podman as-is.
3. **Launcher** in the loop: the `docker run --rm` line above, parameterized by harness; wall-clock `timeout` inside + `docker kill` watchdog outside.
4. **Harness config inside the image**: Claude Code — settings with `permissions.defaultMode: "bypassPermissions"` is unnecessary (flag suffices) but add `deny` rules for `WebFetch` if you want; Codex — `config.toml` with `sandbox_mode = "danger-full-access"`, `approval_policy = "never"`; opencode — `permission: {"*": "allow"}`; pi — nothing.
5. **Kill-switch tests** (acceptance criteria): `:(){ :|:& };:` dies at 512 pids with host untouched; `yes > /dev/null` matrix pegs only its `--cpus`; `dd if=/dev/zero of=big` fills only the volume (size-limited volume or `--storage-opt`); `rm -rf /` destroys only the container; `cat ~/.ssh/id_ed25519` fails (nothing mounted).
6. **Scorer isolation test**: from inside a mutator container, attempt to read/write the scorer volume and reach the scorer container — all must fail; scorer runs same candidate twice → identical score (determinism check).
7. **Throughput check**: measure per-run container overhead vs a warm `docker exec` variant; if startup dominates, switch the inner loop to one container per *candidate* (not per command) — still destroyed between candidates (§E.9).
8. **Later hardening** (optional, in order of value): egress allowlist via `init-firewall.sh` pattern; `--read-only` rootfs + `--tmpfs /tmp` with the venv living in `/workspace`; `--cap-drop ALL`; image digest pinning + `DISABLE_AUTOUPDATER=1` for Claude Code (§B1 devcontainer).
